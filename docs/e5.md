# E5 — Total Cost of Ownership on real measurements

**Article reference:** §7.6. Replaces the synthetic Table 4 with measured
values for B2 vs B3 across mixed context lengths.

## What we measure

`N` HumanEval tasks split across context lengths `{512, 2048, 8192}`,
each run by both **B2 ClassicalMAS** and **B3 HybridINoT**. We collect:

- per-task `C_inf` (USD) using `config.yaml` prices,
- per-task token counts and latencies,
- per-task `pass@1`.

We then compute:

- mean per-task cost difference `Δ = C_inf^{B2} − C_inf^{B3}` and
- monthly extrapolation `Δ · 10 000` tasks/month (article's standard scale),
- 95% bootstrap CI for that monthly delta,
- a price-sensitivity sweep at `±25%` and `±50%` of the configured prices.

## Pass condition for "TCO favours B3"

The article requires the **lower** bound of the 95% CI to be `> 0` AND the
sensitivity sweep to keep the lower bound positive across the `±50%` band.

## How to reproduce

```bash
python -m inot e5 --n 60 --seeds "42,123"
python -m inot view e5
```

Outputs in `results/e5/`:

- `runs.json`, `table.txt`,
- `tco_summary.json` — point estimate, monthly extrapolation, CI,
  full price-sensitivity sweep,
- `fig_tco_extrapolation.png` — bootstrap distribution of monthly deltas,
- `fig_price_sensitivity.png` — line plot of monthly delta vs price perturbation.

## Why this design

- The article emphasises that synthetic TCO numbers are not credible. We
  use whatever cost the **OpenRouter `usage` block** reports for each call
  (with `tiktoken` fallback), so prices are exactly those the user pays.
- The bootstrap is over *task-level* differences, not arch-level averages,
  so it doesn't hide variance.
- The sensitivity sweep is the article's safeguard against price drift; we
  compute it on the measured token mix rather than re-pricing model.
