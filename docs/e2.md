# E2 — Ablations and adversarial scenarios

**Article reference:** §7.3 (E2a, E2b, E2c, E2d).

This experiment quadrant stress-tests every architectural choice that goes
into Hybrid-INoT. It is the article's main internal-validity defence.

## E2a — Component ablation

We compare the full Hybrid-INoT (B3) against three lesions:

| variant | what is removed | tests article claim |
|---|---|---|
| **B3a** | compression Algorithm 2 | "compression carries `γ ≤ 0.3` term" |
| **B3b** | internal critic role `r_crit` | "critic ≠ generator with another instruction" |
| **B3c** | external `r_self` gating loop | "external verifier is the *only* objective signal" |

Each ablation is paired against the full B3 with the **Wilcoxon signed-rank**
test on per-task `MAS_i`, plus 95% bootstrap CI on the mean drop. **Holm–
Bonferroni** controls FWER across the three comparisons. The article's pass
condition: every component must show a *significant* contribution.

## E2b — Critic systematic-error scenario

Procedure (article §7.3):
1. Pick the subset of tasks where B0 fails (`50` in the article spec).
2. Run B3 on this subset.
3. Count how often the *internal critic* picks a candidate whose external
   verification fails (= "critic confidently wrong").

The article alarms at > 20% rate (it then recommends external critic
training).

## E2c — Parallel tools (H3 boundary)

50 tasks from the **Synthetic Tool-Use Suite** (procedurally generated; see
`src/inot/tasks/__init__.py::build_synthetic_tool_use_suite`). Each task
contains `k ∈ {2, 3, 4}` independent sub-functions and deterministic external
tool latencies.

We report two complementary measurements:

- LLM orchestration latency for B2 vs B3 on the same task/seed grid.
- Direct external-tool latency from `inot.tools.synthetic`: Hybrid-style
  serial execution vs Classical-MAS-style parallel execution.

The article's H3 predicts the serial Hybrid-style path will lose its latency
advantage when subtools are truly independent. E2c now tests that directly,
instead of relying only on model wall-clock noise.

## E2d — Metric sensitivity

Re-rank the four ablations by `MAS_i` while perturbing:
- weights `(w_cc, w_dup, w_warn, w_doc)` by ±20%,
- aggregation exponent `λ ∈ {0, 0.25, 0.5, 0.75, 1}`.

Inversions vs the canonical (`λ = 0.5`, `jitter = 0`) ranking are tallied. A
robust metric should produce zero inversions; non-zero counts highlight
parameterisation fragility.

## How to reproduce

```bash
python -m inot e2 --n 50 --seeds "42,123"
python -m inot view e2
```

Outputs in `results/e2/{e2a,e2b,e2c,e2d}/`:

- `runs.json`, `summary.json`,
- `tool_latency_serial.json`, `tool_latency_parallel.json` (E2c),
- `pairwise_vs_full.json` (E2a),
- `fig_ablation_mas.png`, `fig_latency_b2_vs_b3.png`,
- E2d's `summary.json` enumerates every ranking under perturbation.

## Why this design

- Ablations are *paired* on the same task list and seed grid so Wilcoxon is
  legitimate.
- E2b deliberately picks the hardest tasks (those B0 fails), because that's
  where critic confidence has the most leverage — exactly the scenario the
  article worries about.
- E2c's tasks are constructed so that subtask independence is *true*, not
  inferred — the cost-of-coordination argument behind H3 needs that.
- E2d uses the same `MAS_i` form prescribed in formula (20); only weights
  and `λ` move. This isolates metric stability from any modelling choice.
